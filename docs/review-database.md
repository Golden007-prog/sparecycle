# SpareCycle Review database

This release uses Supabase Auth and PostgreSQL organization membership. Browser workspace profiles in the original repair planner remain a separate local feature and do not grant Review access. Authenticated requests validate their access token with `auth.getUser`; every database request then uses the same user JWT and publishable key. There is no service-role CRUD client.

Apply the checked-in `supabase/migrations` files in filename order to the selected new SpareCycle project. The initial `20261010043058_sparecycle_review.sql` creates nine public tenant tables and four private operational tables. The follow-up `20261010045016_review_failed_checkpoint_isolation.sql` keeps failed job checkpoints from becoming another job's starting state and revokes public execution on Supabase's automatic RLS event-trigger function when present. Both filenames were generated with the Supabase CLI migration command. These migrations do not modify existing application tables or issue account upgrades. Deploying SQL is a separate step from configuring authentication, email delivery and GitHub access.

The third migration, `20261010050058_review_query_indexes.sql`, adds lookup indexes for invalidating changes by laptop, reconnecting projects, and counting the global rolling job window. Existing evidence uniqueness already supports its ordered history query, and the active-job partial index supports active change lookups. Creator/actor and invitation foreign keys are not indexed merely to remove advisor INFO messages: no corresponding application lookup or parent-deletion path exists in this pilot. Reassess them when account deletion, retention or larger operational workloads are implemented.

Public tables have RLS and authenticated SELECT grants. Their policies look up the caller in the membership table, excluding anonymous accounts. Direct client INSERT, UPDATE and DELETE are revoked. The exposed `review_mutate` wrapper uses invoker rights; its private implementation uses definer rights only to enforce transactional invariants and bootstrap an organization with its first owner. The private implementation checks a real Auth identity, membership, the action-specific role, and—for worker actions—a separate server proof. Both functions revoke anonymous and default PUBLIC execution. The private schema must remain excluded from the Supabase Data API exposed schemas.

The deployer must generate a cryptographically random `REVIEW_WORKER_SECRET` of at least 32 characters, store it only in server environment settings, and insert its SHA-256 hash into `review_private.runtime.worker_secret_hash`. The runtime table has no client grants. Never put the raw secret in a checked-in migration, a browser variable, an API response, a model prompt or a log. The deployer can update the hash with a parameterized privileged SQL query:

```sql
update review_private.runtime
set worker_secret_hash = encode(sha256(convert_to($1, 'UTF8')), 'hex'),
    budget_limit_cents = 100
where singleton = true;
```

The `$1` parameter is the new server secret. If the SQL console cannot bind parameters, use an approved secret-handling deployment tool instead of committing a literal. Without a configured hash, trusted result writes fail closed. This worker proof adds a separate boundary because a browser can call Supabase RPCs directly: a user JWT alone cannot be accepted as proof that tests passed or repository ownership was verified.

Owners and admins manage organization settings and invitations. Only owners may invite another admin; invitations cannot create owners. Reviewers and technicians may create laptops, append evidence, create changes and request jobs. Viewers can read their organization. Only owners, admins and reviewers may approve, and the change author cannot approve their own change. Invitations combine two cryptographically random UUIDs, are stored hashed, expire in 24 hours and are consumed once. Redeeming an invitation does not replace an existing membership or escalate its role. Links are copied by the user; this implementation sends no email.

Evidence is append-only. Each laptop increments its evidence revision transactionally, while a change retains the snapshot it actually investigated. New evidence clears prior approval and verification and marks open changes as needing evidence. A fresh investigation takes the latest revision and resets its prior artifacts. In-flight results for an older revision are discarded, while their actual inference cost is still recorded. Approval binds the current revision, base commit and patch hash, requires baseline failure and candidate success, and requires a separate review summary. Reconnecting a repository resets existing review artifacts and is blocked while an associated stage is active.

Job reservations use a global credit ledger and an organization/month ledger in the same transaction. Defaults are a 100-cent organization monthly cap and a 100-cent aggregate service cap. These are internal cost estimates and do not change the provider's billing settings or purchase credits. The aggregate cap is intentionally not automatically reset; a deployer must review provider credits before increasing/resetting it. An organization admin cannot raise their limit above that aggregate ceiling. A user can own at most three organizations. Reservations also cap new jobs at 20 per organization and 100 per service over 24 hours, with two active jobs per organization and four service-wide. These limits include stages with a zero inference reservation and prevent repeated organization creation from multiplying the trial credit allowance. An idempotent repeat returns its existing job without using another slot.

Only one stage may be active for a change. Idempotency keys are unique within an organization and cannot be reused for a different stage/change. Claiming a job obtains a 75-second lease token, and only its current token can settle the result. Private checkpoints carry artifacts between stages. A separate trusted `saveCheckpoint` operation persists an in-flight marker before external work without releasing the lease or reservation. An interrupted model call whose outcome is unknown must not be retried against the same reservation; the orchestrator settles it conservatively and requires a separately reserved new job. The browser never receives source checkpoints, worker proofs or lease tokens. A waiting continuation retains unused reservation; a final result records actual cost and releases the remainder. Cancelling an actively leased job retains its credit reservation until the worker settles, so cancellation cannot make credits already being spent available to another job.

Operational limitations are explicit. An interrupted worker may leave reserved credits requiring operator reconciliation; this is safer than releasing a reservation while a provider operation may still run. A user JWT is required to resume a stage, so an expired session requires signing in again. The pilot overview returns bounded latest records (200 per main collection, 500 evidence entries, 100 audit events); it is not a full fleet export. GitHub publication and SQL cannot share one atomic transaction, so the publisher must use an idempotent branch/PR marker and recheck current approval immediately before the GitHub write. A new evidence revision during that external write can invalidate a PR that was just opened; a human must review it.

The checked-in tests execute the actual migration and SQL functions in PGlite PostgreSQL, with a minimal Auth schema replacing the external Supabase Auth service. They cover tenant separation, role boundaries, immutable evidence/audit, invitation expiry/replay, worker proof, reservation/lease conflicts, stale evidence, independent approvals and cancellation settlement. This validates PostgreSQL behavior locally; it does not claim the production Supabase RLS, mail service, OAuth provider or connection settings have been exercised. After deployment, run Supabase security/performance advisors and a two-account tenant-isolation smoke test against the actual project.

Sources checked during implementation: [Supabase Auth context and live user validation](https://supabase.com/docs/guides/functions/auth-legacy-jwt), [Supabase data security](https://supabase.com/docs/guides/database/secure-data), and [Supabase changelog](https://supabase.com/changelog). The September 2026 PostgreSQL upgrade notice concerns legacy crypto/index behavior; this schema uses no legacy cipher, ltree or btree_gist dependency.
