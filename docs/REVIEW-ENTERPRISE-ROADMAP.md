# SpareCycle Review: enterprise delivery map

SpareCycle Review connects a laptop's evidence to a reviewed software change: organization → passport → evidence revision → repository snapshot → proposed patch → isolated tests → independent approval → draft PR. The differentiating product idea is this chain of evidence and accountability across physical assets and software, including a clear stop when the evidence points to a physical repair. It is a product hypothesis to validate with design partners, not a claim that no other vendor offers similar capabilities.

The supplied 200-item document is tracked in [review-enterprise-backlog.csv](review-enterprise-backlog.csv). Every original number appears exactly once, with its original capability, delivery status, bounded scope, acceptance gate and priority. Its current mapping is **8 implemented foundations, 20 narrow pilot mappings, 129 later items and 43 items requiring domain validation**. A foundation or pilot mapping may satisfy only part of a broad requested item; the scope column identifies the gap. These counts are not 200 shipped features, and they do not turn the earlier 520-story catalog into a shipped-feature count.

“Implemented foundation” means code and local tests exist for an underlying control. “Current narrow pilot” means a related bounded workflow is represented in the current build, subject to the actual configured integration and live test results. Neither label proves a cloud account is provisioned or a physical device is certified. “Later” means not implemented in this release. “Needs validation” means the proposed capability also needs external ground truth, vendor authority, independent assessment or a corrected premise before it can responsibly be offered.

The first customer workflow stays small. An administrator creates an organization, invites a second reviewer, registers a laptop passport and appends diagnostic evidence. The administrator connects a selected GitHub repository and chooses the approved diagnostics file and unchanged tests. A technician opens a recovery change. Nebius Nemotron classifies the evidence, proposes a narrowly scoped parser fix if appropriate, and separately reviews the candidate after isolated tests. The reviewer approves the exact evidence revision, commit and patch; the service creates a draft PR. A merged software PR does not mark the physical laptop repaired.

The current model roles use Nebius Token Factory with explicit routing among the verified catalog identifiers for Nano, Lightning, Super and an administrator-enabled Ultra escalation. Available catalog entries are not proof of equal quality, latency or account access for every endpoint. Each stage uses bounded inputs, strict output validation, server-owned tools, a durable credit reservation and private continuation state. LangSmith receives metadata without raw evidence or source. A provider outage, missing sandbox entitlement, unsupported language or stale approval produces a visible stop rather than a simulated success.

The best expansion path follows the evidence chain. First support one real IT team and a small diagnostics repository, collect failures where the system correctly abstains, and measure time from an accepted evidence bundle to a reviewer-approved PR. Then add one language profile and one read-only MDM connector, with a separate evaluation set for each. Fleet write access, hardware risk scores, cross-device learned recipes, remote rollback and sanitization should follow only when their evidence and authorization gates are demonstrated. Hundreds of shallow toggles would weaken this product more than a few reliable end-to-end workflows strengthen it.

Several requested capabilities need precise interpretation. Item 32's `apt-get` → `apt` example is not a general modernization rule; a vendor migration needs an actual deprecation notice and script compatibility tests. Items 61 and 62 can collect control evidence but cannot establish SOC 2 or ISO 27001 certification. Items 81–100 describe simulations that may test software behavior without reproducing physical laptop faults. Item 183 can estimate avoided emissions using disclosed assumptions, but that is not a carbon offset credit. Item 186 requires verified sanitization evidence rather than a generated certificate. Item 187 cannot claim software restores chemically degraded battery capacity. Item 199's clean install cannot by itself prove all corporate data was erased.

Business validation should measure outcomes customers can verify: fewer unsupported replacements, less technician investigation time, fewer unsafe fleet changes, and reviewable repairs that preserve device life. The natural buying groups are IT operations, internal endpoint engineering teams and refurbishment operators. Test a paid pilot organized around connected repositories and active assets, with a clearly stated inference allowance and consumption ceiling; do not publish invented willingness-to-pay or market-size numbers. The first design partners should bring both a responsible reviewer and resolved historical incidents so evaluation can compare against outcomes instead of plausibility.

The release report must distinguish local unit/integration results, hosted tenant-isolation results, real Nebius inference, actual isolated test execution and actual draft PR publication. A passing local fixture is valuable evidence but cannot stand in for any of those other checks. Current live readiness is recorded in the release notes, not inferred from this roadmap.
