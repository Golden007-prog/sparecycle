The best first use case

SpareCycle Review's first customer hypothesis is a refurbishment team that owns its diagnostic software. A technician observes a problem. An engineer needs a controlled fix and proof. Follow that handoff into the working backend, then the investment roadmap.

A useful first workflow

A technician records passport evidence. An engineer defines the software issue. A separate reviewer inspects the tested candidate. The output is a draft pull request for code review. Passing software tests never certify a physical repair.

Start with versioned evidence

The company workspace connects a passport, project, and change request to a particular evidence revision. These records and accounts are synthetic. The provider calls, test executions, and resulting draft pull requests actually happened.

The reproduced parser failure

Here, a valid zero-percent battery reading becomes missing data. That can mislead diagnosis. The request defines expected behavior before generation. The backend compares original and candidate code using exactly the same test cases.

What actually ran on the backend

These saved private-run timestamps document Nano investigation, passing verification, Super review, and a draft created after separate approval. This is recorded execution evidence. The intervals include pauses, so they are not a latency benchmark.

Nebius and NVIDIA have different roles

Nebius Token Factory hosts NVIDIA Nemotron inference. GitHub Actions runs isolated tests; Nebius Sandboxes are not the live runner. Relevant private code goes to Nebius. Test isolation does not mean reasoning stays on the company's laptop.

Route by stage, measure the result

Lightning investigated the public case; Nano investigated the private pilot. Super proposed and independently reviewed both candidates. Ultra was separately checked, not proven better. Future routing should follow evaluations of correctness, latency, and cost.

Real provider usage, with limits

The supplied Nebius usage view records four model tiers. It confirms usage, not correctness. Rounded cost buckets cannot establish cost per accepted fix. That requires reconciled usage across successful and rejected attempts.

What the AI harness controls

The harness bounds evidence, requires structured output, and validates changes. The model has no shell, network, or publishing tool. Trusted server code controls testing and publication. The model proposes; the application authorizes each transition.

Bound the stage before it starts

A reserved stage budget, forty-second deadline, and bounded input and output constrain each call. Current execution is a pure JavaScript diagnostic-parser change. Broader languages and dependencies need additional test profiles and evaluations.

Bind the fix to exact inputs

The candidate is bound to its base commit, patch hash, and evidence revision. Proof and approval refer to those inputs. Changed code or evidence invalidates old approval. Passing proof cannot authorize a different candidate.

Reproduce, then verify the same tests

GitHub Actions executes both versions in a network-disabled container. The original has one failure and three passes. The candidate passes all four unchanged test cases. That proves covered behavior, not every input or hardware condition.

Require a separate approval

The model reviewer receives fresh context. A different organization member approves the exact tested candidate. The private pilot rejected self-approval. The QA accounts are synthetic; this demonstrates a permission boundary, not customer adoption.

The real public draft pull request

This actual App-created draft contains the tested patch and verification metadata. Technician narratives remain in the workspace. A maintainer still reviews the code. Nothing is automatically merged or marked physically repaired.

The verified private-repository pilot

Encrypted dispatch ran verification in the same private repository. One baseline failure became four unchanged test cases passing. A separate approval preceded a real draft. This validates one fixture. Private setup currently requires an operator-approved verifier and repository key.

Software, hardware or missing evidence

Software can proceed to a bounded patch. Hardware goes to workshop review. Missing evidence calls for more evidence. The classification is implemented; only the software branch is demonstrated by the completed live fixture.

How Review fits the recovery planner

The Workshop planner allocates declared parts, technician time, and budget. Today it is browser-local, without automatic inventory synchronization into Review. A shared record connecting planning, diagnosis, and verified repair outcomes is future work.

Organization access and trace privacy

An outsider organization request was rejected. LangSmith traces keep metadata, excluding source and diagnostic narratives from trace inputs and outputs. These are specific controls and checks. An independent security assessment is still future work.

How a design partner should start

Start with one owned diagnostic project, one repeatable failure, versioned evidence, and a separate reviewer. A commercial hypothesis is a supervised paid pilot, then a company subscription with explicit usage caps. Pricing and demand remain unvalidated.

Current implementation gaps

Google login works; custom company email remains deferred. Managed SSO needs identity-policy enforcement and deprovisioning, plus provider setup. Runner coverage remains constrained. Customer repair rates and field savings need real pilots measured against recorded baselines.

What investment should unlock

Begin customer pilots alongside reliable onboarding. Next, fund recoverable jobs, cancellation, reconciled usage, and evaluations. Then enforced SSO, shared data, and broader tested runners. Dedicated Nebius capacity is a future option when measured load or residency needs justify it.

Measure value before scaling

Measure accepted fixes, regressions, review time, and total cost per accepted fix: inference, verification, and support, including rejected attempts. Each funded stage needs an acceptance gate. Measure physical throughput separately; environmental claims require field evidence.
