The best first use case

SpareCycle joins a refurbishment coordinator's planning workflow with a diagnostics engineer's code review. Follow the working product, recorded backend proof, and the investment gates.

A useful first workflow

A technician records an observation. An engineer defines a supported software issue. A separate reviewer inspects the tested candidate. Every handoff keeps its evidence.

Pilot Operations records the handoff

Pilot Operations freezes the validated plan, then records per-device progress, blockers, assignment and due dates, actual effort, costs and evidence-backed manual checks. A local scorecard distinguishes proposed devices from technician-reported outcomes. Export a handoff or backup. These records neither consume shared stock nor certify a physical release.

A real Tavily search, summarized on Nebius

A public model question invokes Tavily in the application backend. The server filters official documentation, assigns source IDs, and passes only bounded snippets to NVIDIA Nemotron on Nebius. The result shows its sources, uncertainties and next checks. A matched citation is not a hardware diagnosis: the technician must inspect the source and the actual device.

Start with versioned evidence

The company workspace connects a passport, project, and change request to a particular evidence revision. These records and accounts are synthetic. The provider calls, test executions, and resulting draft pull requests actually happened.

The reproduced parser failure

Here, a valid zero-percent battery reading becomes missing data. That can mislead diagnosis. The request defines expected behavior before generation. The backend compares original and candidate code using exactly the same test cases.

What actually ran on the backend

These saved private-run timestamps document Nano investigation, passing verification, Super review, and a draft created after separate approval. This is recorded execution evidence. The intervals include pauses, so they are not a latency benchmark.

Nebius and NVIDIA have different roles

Nebius Token Factory hosts inference. NVIDIA supplies Nemotron. GitHub Actions executes tests; Supabase protects organization records. These are distinct services, each with a defined job.

Route by stage, measure the result

Nano and Lightning can investigate. Super writes and freshly reviews non-Ultra cases. Ultra is an explicit operator-enabled escalation, not an automatic promise of better quality.

Real provider usage, with limits

The supplied usage view records all four tiers. Its rounded cost buckets are provider evidence, not an exact invoice or comparative benchmark.

What the AI harness controls

The harness bounds evidence, requires structured output, and validates changes. The model has no shell, network, or publishing tool. Trusted server code controls testing and publication. The model proposes; the application authorizes each transition.

Bound the stage before it starts

A model stage has a forty-second deadline, a bounded context, strict output and reserved spend. There is no automatic paid retry after an uncertain result.

Bind the fix to exact inputs

Evidence revision, repository commit and candidate hashes travel together. Changed inputs require fresh verification and approval; a passing test cannot bless another patch.

Reproduce, then verify the same tests

GitHub Actions executes both versions in a network-disabled container. The original has one failure and three passes. The candidate passes all four unchanged test cases. That proves covered behavior, not every input or hardware condition.

Require a separate approval

The model reviewer receives fresh context. A different organization member approves the exact tested candidate. The private pilot rejected self-approval. The QA accounts are synthetic; this demonstrates a permission boundary, not customer adoption.

The real public draft pull request

This actual App-created draft contains the tested patch and verification metadata. Technician narratives remain in the workspace. A maintainer still reviews the code. Nothing is automatically merged or marked physically repaired.

The verified private-repository pilot

The private pilot used Nano investigation and Super patching and review. Encrypted source went to a pinned verifier in the same private repository. Independent approval preceded the real draft.

Software, hardware or missing evidence

Software can proceed to a bounded patch. Hardware goes to workshop review. Missing evidence calls for more evidence. The classification is implemented; only the software branch is demonstrated by the completed live fixture.

How Review fits the recovery planner

The Workshop allocates declared parts, time and budget. It stays browser-local; authenticated Review has separate organization records. Their handoff is explicit, without automatic inventory synchronization.

The reviewer attention queue

Review insights compare loaded evidence revisions, verification references and approval bindings. Filters bring stale records, delayed jobs and cases requiring attention into one queue. This is read-only guidance. It does not rerun tests, validate repository head, change permissions, or execute a job. Refresh the server record before deciding.

Organization access and trace privacy

An outsider organization request was rejected. LangSmith traces keep metadata, excluding source and diagnostic narratives from trace inputs and outputs. These are specific controls and checks. An independent security assessment is still future work.

How a design partner should start

Start with one owned diagnostics project, one reproducible failure and a separate reviewer. A supervised pilot and usage-capped subscription are commercial hypotheses that still need buyer validation.

Current implementation gaps

Google sign-in works. Company email is deferred; managed SSO requires enforcement and deprovisioning. Broader runners and physical repair outcomes need additional implementation and real field measurement.

What investment should unlock

Fund reliable onboarding and supervised pilots first. Then failure recovery, usage reconciliation and evaluations. Enforced SSO, shared stock and broader runner profiles follow only after their acceptance gates.

Measure value before scaling

Measure accepted fixes, regressions, review time and total cost, including rejected attempts. The selected two hundred roadmap capabilities are planned work with acceptance criteria, not two hundred shipped features.
